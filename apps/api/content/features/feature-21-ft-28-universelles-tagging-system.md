<h1>FT (28): Universelles Tagging-System</h1>
<h2>Metadaten</h2>
<ul><li>Status: Abgeschlossen</li><li>Typ: Feature</li></ul>
<h2>Ziel / Zweck</h2>
<p>Ein generisches, domänenübergreifendes Tagging-System wird eingeführt, das an allen zentralen Domänenobjekten (Projekt, Kunde, Mitarbeiter, Termin) konsistent nutzbar ist. Tags ergänzen zunächst den bestehenden Projektstatus (FT 15) und können diesen mittelfristig vollständig ablösen. Das System ersetzt rudimentäres Mehrfach-Marking durch eine sauber normalisierte, rollengeschützte Infrastruktur.</p>
<h2>Fachliche Beschreibung</h2>
<p>Das System besteht aus zwei Ebenen: einer zentralen <code>tags</code>-Tabelle sowie je einer Join-Tabelle pro Domänenobjekt (<code>project_tags</code>, <code>customer_tags</code>, <code>employee_tags</code>, <code>appointment_tags</code>).</p>
<p>Jeder Tag besitzt einen eindeutigen Namen und eine Farbe. Die Farbe wird per freiem Color-Picker gewählt und dient der visuellen Unterscheidung in Listen- und Kalenderansichten. Tags können in einer zentralen Verwaltungsansicht angelegt, umbenannt, neu eingefärbt und gelöscht werden. Die Zuweisung erfolgt im Kontext des jeweiligen Domänenobjekts. Filtern und Suchen nach Tags ist in allen Listenansichten der jeweiligen Domäne vorgesehen.</p>
<p><strong>Default Tags</strong> sind systemseitig vordefinierte Tags, die beim initialen Setup oder per Migrations-Skript angelegt werden. Sie sind geschützte System-Tags und dürfen nicht wie frei verfügbare Tags durch Nutzer zugewiesen, entfernt, gelöscht oder umbenannt werden. Änderungen an Default Tags einschließlich Umbenennung, Farbe und Löschung sind serverseitig geschützt. In der Verwaltungsansicht sind Default Tags visuell als geschützt gekennzeichnet (z. B. Schloss-Icon).</p>
<p>Welche System-Tags im Tag-Picker einer Domäne erscheinen, ist pro Domäne geregelt: Bei <strong>Mitarbeitern</strong>, <strong>Kunden</strong>, <strong>Terminen</strong> und <strong>Projekten</strong> sind geschützte System-Tags aus dem generischen Picker ausgeschlossen. Der Storniert-Tag wird ausschließlich über den Storno-Workflow gesetzt. Der Reklamation-Tag wird ausschließlich über die fachlichen Reklamationsfunktionen am Termin oder am Projekt gesetzt und entfernt. Eine manuelle Zuweisung oder Entfernung über die generischen Tag-Funktionen ist für Nutzer nicht zulässig.</p>
<h2>Regeln &amp; Randbedingungen</h2>
<ul><li>Ein Tag-Name ist eindeutig innerhalb der zentralen <code>tags</code>-Tabelle.</li><li>Tags können beliebig vielen Einträgen aller Domänen zugewiesen werden.</li><li>Das Löschen eines Tags entfernt automatisch alle zugehörigen Join-Einträge (Cascade Delete).</li><li>Tags dürfen nur vom Admin gelöscht werden und nur, wenn keine Relationen bestehen.</li><li>Default Tags besitzen ein <code>is_default</code>-Flag und werden serverseitig vor Mutation geschützt – der Schutz wird nicht allein über die UI, sondern per API-Guard durchgesetzt.</li><li>Die Farbwahl erfolgt über einen freien Color-Picker ohne vordefiniertes Farbset.</li><li>Disponenten können Tags zuweisen und entfernen, aber keine Tags anlegen, umbenennen oder löschen.</li><li>Disponenten und Administratoren können geschützte System-Tags nicht über generische Tag-Zuweisungen setzen oder entfernen. Dafür müssen die jeweiligen fachlichen Workflows verwendet werden.</li><li>Die Sichtbarkeit von System-Tags im Tag-Picker ist domänenspezifisch geregelt (siehe Fachliche Beschreibung). Die Filterung erfolgt serverseitig über den <code>/api/tags?domain=</code>-Parameter.</li></ul>
