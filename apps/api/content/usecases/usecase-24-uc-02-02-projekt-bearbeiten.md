<h1>UC 02/02: Projekt bearbeiten</h1>
<h2>Metadaten</h2>
<ul><li>Feature: <a href="../ft-02-projekte.md">FT (02): Projekte</a></li></ul>
<h2>Akteur</h2>
<p>Administrator, Disponent</p>
<h2>Ziel</h2>
<p>Projektdaten ändern, mit strikter Kundenkonsistenz und Schutz vor parallelen Überschreibungen.</p>
<h2>Vorbedingungen</h2>
<ul><li>Das Projekt existiert.</li><li>Der Akteur ist authentifiziert.</li><li>Der Akteur besitzt Änderungsrechte (Disponent oder Administrator).</li><li>Das Projekt besitzt ein Versionsmerkmal (Optimistic Locking).</li></ul>
<h2>Ablauf</h2>
<p>1. Der Akteur öffnet ein Projekt.<br>2. Der Akteur ändert zulässige Felder (Titel, Beschreibung, Aktiv-Status).<br>3. Der Akteur versucht, den Kunden des Projekts zu ändern.<br>1. Das System prüft: Hat das Projekt mindestens einen Termin zugeordnet?<br>2. Falls <strong>JA:</strong> Das System blockiert den Kundenwechsel mit Fehlermeldung. Der Kundenwert ist readonly.<br>3. Falls <strong>NEIN:</strong> Der Akteur wählt einen neuen Kunden. Das System prüft Existenz und Aktivstatus des neuen Kunden. Das System speichert die Kundenänderung und aktualisiert den <code>customer_id</code>-Wert aller zugeordneten Termine kaskadierend.<br>4. Optional ändert der Akteur strukturierte Auftragspositionen, darunter das Artikellistenfeld <strong>Sauna</strong>.<br>1. Wenn dadurch ein anderes Sauna-Modell gewählt wird und der Projektname nicht bereits dem neuen Modell entspricht, bietet der Projekt-Speichern-Review an, den Projektname anzupassen.<br>2. Bestätigt der Akteur, setzt das System den Projektnamen auf den Namen des gewählten Sauna-Modells.<br>3. Lehnt der Akteur ab, bleibt der bisherige Projektname unverändert.<br>5. Optional ändert der Akteur projektbezogene Tag-Zuordnungen gemäß FT (28).<br>6. Wenn das Projekt aus einem Doc-Extract-Draft stammt und der Akteur nachträglich Projektdaten, Artikelliste oder Projekttitel manuell geändert hat, zeigt der Projekt-Speichern-Review nur die dadurch erneut offenen Speicherentscheidungen.<br>7. Das System prüft das Versionsmerkmal serverseitig. Bei Übereinstimmung speichert das System die Änderungen und erhöht die Version.</p>
<h2>Alternativen</h2>
<ul><li>Projekt nicht vorhanden → HTTP 404.</li><li>Akteur nicht authentifiziert → HTTP 401.</li><li>Akteur ohne Änderungsrechte → HTTP 403.</li><li>Projekt hat Termine → Kundenwechsel wird blockiert (HTTP 409 BUSINESS_CONFLICT).</li><li>Neuer Kunde existiert nicht → HTTP 422.</li><li>Neuer Kunde ist inaktiv → HTTP 409 INACTIVE_ENTITY_ASSIGNMENT.</li><li>Versionskonflikt (Optimistic Locking) → HTTP 409 VERSION_CONFLICT, Akteur muss neu laden.</li><li>Sauna-Modell wird nicht fachlich geändert → System zeigt keine Projektnamen-Rückfrage.</li><li>Abbruch → keine Änderung wird gespeichert.</li><li>Technischer Fehler → HTTP 500, keine Änderung.</li></ul>
<h2>Ergebnis</h2>
<p>Das Projekt ist aktualisiert. Der Kundenwert bleibt stabil, solange das Projekt Termine besitzt. Bei einem zulässigen Kundenwechsel werden alle zugeordneten Termine auf den neuen Kunden aktualisiert. Alle abhängigen Ansichten sind konsistent.</p>
